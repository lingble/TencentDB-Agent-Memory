# DeepSeek Harness (dsh)

> agentSource: `dsh` | Protocol: **Anthropic Messages** (v0.2+) / OpenAI Chat (v0.1.x)
>
> To import local history into Memory Hub, see the [Asset Import Guide](./asset-import.md).

> ⚠️ **Major change on 2026-09-29**: starting with dsh v0.2.0-rc.1, the adapter protocol and the config entry point both changed.
> The old `~/.dsh/settings.yaml` setup (dsh v0.1.x + setup-proxy.sh) is **obsolete**;
> see Section 1 below.

## 0. Migrating from dsh v0.1 to v0.2 (since 2026-09-29)

### 0.1 Side-by-side config comparison

The same thing is written completely differently across the two dsh major versions. The config generated by the old setup-proxy.sh
**will not even boot** under v0.2 (the loader doesn't accept the settings.yaml shape, and the plugin id was renamed).

| Item | dsh v0.1.x (old) | **dsh v0.2+ (current)** |
|---|---|---|
| Config entry file | `~/.dsh/settings.yaml` (top-level plugin section) | `~/.dsh/profiles/web/cordis.patch.yml` (loader patch array) |
| Plugin id | `@deepseek-ai/dsh-llm-deepseek` | `@deepseek-ai/dsh-llm-deepseek-api-key` |
| Upstream protocol | OpenAI Chat Completions | **Anthropic Messages** |
| Request endpoint | `${baseURL}/chat/completions` (no /v1) | `${baseURL}/v1/messages` (always with /v1) |
| Anthropic header | None | `anthropic-version: 2023-06-01` always sent |
| User input payload | `content: string` (plain text) | `content: [{type:"text",text}, ...]` (Anthropic block array) |
| Tool result payload | `role:"tool" + tool_call_id` (message level) | `role:"user" + content[].type:"tool_result"` (block level) |
| Credential storage | Flat in settings.yaml | `refs:` section of `~/.dsh/.credentials.yaml` (chmod 600 strictly required) |
| Build requirement | npm install is enough | Recommended: `git pull && pnpm install && pnpm run build` (rc versions iterate fast) |

### 0.2 Matching proxy-side fixes (landed 2026-09-29 → 09-30)

The first category above is upstream dsh changes. The second category is **proxy-side support lagging behind**, which only surfaced once the first category was fixed
and real dsh v0.2 requests hit the proxy. This round fixed 5 issues, all in
`team-proxy@develop_server_team`:

| # | Location | Symptom |
|---|---|---|
| 1 | `src/session/dsh/form.ts` | Only had an OpenAI SSE builder, so Anthropic clients couldn't parse the form |
| 2 | `src/session/dsh/form.ts` | ASSET_CONFIRM_YES used a half-width comma that didn't match the full-width one in the CB extractor → the form popped up in a loop after selection |
| 3 | `src/session/codebuddy/cleaner.ts` | Only recognized OpenAI `role:"tool"+tool_call_id`, not Anthropic `role:"user"+tool_result` → team/agent/task stage answers couldn't be read |
| 4 | `src/agent-adapters/dsh.ts` | `extractUserText` only accepted strings, not Anthropic content block arrays → mem commands weren't recognized |
| 5 | `src/anthropicHandler.ts` | 3 `buildMemResponse` return points were missing the `maybeFixDshStreamTail` wrapper → dsh's strict parser reported `STREAM_CLOSED` |

Items 3, 4 and 5 are edge cases in the CB state machine chain that dsh reuses, where old proxy code assumed the OpenAI wire shape;
Anthropic branches have now been added for all of them. Zero impact on CC/CB/WB/opencode/codex.

### 0.3 Migrating from v0.1 to v0.2 in 3 steps

1. **Pull the latest dsh**: `cd deepseek-harness && git pull && pnpm install && pnpm run build` (at least `v0.2.0-rc.1`)
2. **Back up + switch config**:
   ```bash
   TS=$(date +%Y%m%d_%H%M%S)
   cp ~/.dsh/settings.yaml    ~/.dsh/settings.yaml.bak.$TS 2>/dev/null   # back up the old setup
   cp ~/.dsh/.credentials.yaml ~/.dsh/.credentials.yaml.bak.$TS
   # rewrite cordis.patch.yml + the .credentials.yaml refs section per §1.1 / §1.2
   ```
3. **Proxy must be at least develop_server_team @2026-09-30** (includes the 5 fixes above). Running dsh v0.2 against an older proxy
   hits these in sequence: form can't be parsed → form pops up in a loop → answers can't be read → mem doesn't work → mem reports STREAM_CLOSED.

## 1. Client configuration (dsh v0.2+)

Starting with v0.2, dsh moved the config entry point from `~/.dsh/settings.yaml` to a cordis
patch under the **profile directory**, and stores credentials separately in `~/.dsh/.credentials.yaml`. The internal plugin id also changed from
`dsh-llm-deepseek` to `dsh-llm-deepseek-api-key` (the default login variant).

### 1.1 Profile patch file

`~/.dsh/profiles/web/cordis.patch.yml` (the profile name defaults to `web`, used when launching with `dsh web`):

```yaml
- id: llm-deepseek
  name: "@deepseek-ai/dsh-llm-deepseek-api-key"
  config:
    apiKeyEnv: PROXY_USER_KEY
    # ⚠️ No /v1 — the dsh anthropic adapter internally builds `${baseURL}/v1/messages`
    # see dsh source packages/llm/llm-deepseek/src/messages-api.ts:14-17
    baseURL: http://<proxy-host>:8096/dsh/<spaceId>
    reasoningEffort: high
    models:
      - id: deepseek-v4-pro
        name: DeepSeek V4 Pro
        contextWindow: 128000
        maxTokens: 8192

- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: deepseek-official
    model: deepseek-v4-pro
    reasoningEffort: high
```

### 1.2 Credential file

`~/.dsh/.credentials.yaml` (permissions strictly required: chmod 600):

```yaml
version: 1
refs:
  PROXY_USER_KEY: <your business user_key, obtained from the platform>
```

### 1.3 Strict permission requirements (checked at dsh startup)

```bash
chmod 700 ~/.dsh
chmod 600 ~/.dsh/.credentials.yaml
```

### 1.4 Request paths

**dsh v0.2+ uses the Anthropic protocol**; the adapter hardcodes `${baseURL}/v1/messages` +
the `anthropic-version: 2023-06-01` header (source `packages/llm/llm-deepseek/src/adapter.ts:120-131`).
Proxy routes hit:

- `POST /dsh/:spaceId/v1/messages` ← dsh v0.2+ main path
- `POST /dsh/:spaceId/v1/messages/count_tokens` ← auxiliary endpoint

The old OpenAI paths (dsh v0.1.x users only) are also kept for compatibility:
- `POST /dsh/:spaceId/v1/chat/completions`
- `POST /dsh/:spaceId/chat/completions`

### 1.5 Launch & verify

```bash
cd /path/to/deepseek-harness
git pull                 # at least v0.2.0-rc.1 (since 2026-09)
pnpm install && pnpm run build
pnpm dsh web --no-open --port 3081 --host 127.0.0.1
# → dsh web: http://127.0.0.1:3081/?token=xxx
```

Open that URL in a browser and send "hi"; the proxy returns the session-init form (see Section 3).

## 1.6 Desktop client configuration (DeepSeek Harness Desktop)

> Tested 2026-10-08: dsh desktop `0.2.1-alpha.1` (Electron shell + Node Host child process) is **100% equivalent** to the CLI/Web version
> at the LLM protocol layer — the `packages/llm/*` code is shared, and the Electron shell takes no part in
> any outbound LLM fetch. So **the desktop version is supported with zero proxy changes**; you just need to use the right UI config entry.

### 1.6.1 There are three config entries; only the second one works

On the desktop "Settings → Models" page, DeepSeek-type providers are shown as **three cards**:

![dsh desktop model settings](./imgs/desktop-model-settings.png)

| Card | Internal plugin | Protocol | Headers | **Proxy support status** |
|---|---|---|---|---|
| ① DeepSeek account | `@deepseek-ai/dsh-llm-deepseek-account` | Anthropic Messages | No `x-deepseek-harness-session-id` (passes through the account token; not our integration model) | ❌ Not applicable |
| ② **DeepSeek (deepseek-official)** ← red box | `@deepseek-ai/dsh-llm-deepseek-api-key` | Anthropic Messages | **Full set of `x-deepseek-harness-*` headers** (user-id / session-id / compact) | ✅ **Configure only this one** |
| ③ Custom settings / Add model provider | `@deepseek-ai/dsh-llm-pi-ai` | One of OpenAI Chat / Responses / Anthropic | ⚠️ **No `x-deepseek-harness-*` headers at all** (the pi-ai adapter filters them out) | ❌ session_id lost → proxy session-init form never appears |

### 1.6.2 Why only the second one works (wire criterion)

As with CLI/Web, on desktop **only requests going through the `llm-deepseek-api-key` adapter (i.e. the "DeepSeek deepseek-official" card)
carry the full set of dsh identification headers**:

```http
POST /dsh/<spaceId>/v1/messages HTTP/1.1
authorization: Bearer <proxy user_key>
anthropic-version: 2023-06-01
x-deepseek-harness-user-id: <anonymous UUID>
x-deepseek-harness-session-id: session-<uuid>      ← ★ entry criterion for proxy session-init
x-deepseek-harness-compact: 1                      ← only on compaction requests
user-agent: deepseek-harness/0.2.1-alpha.1 (+...)
```

With the third "Custom settings" card, the underlying adapter is `llm-pi-ai` (source
`packages/llm/llm-pi-ai/src/adapter.ts:204-212`), whose `requestHeaders`
**keeps only the attribution header and filters out the entire `x-deepseek-harness-*` family**. As a result, on the proxy side:

- `conversationId=null` → the `sessionInit` condition `conversationId && !isAuxiliary` is not met
- → `injectedSkipped=true` → the session-init form **never appears**
- → everything is passthrough; injection / archiving / mem commands are all skipped

This is the same pitfall as on the CLI side: "don't mount the pi-ai plugin in `~/.dsh/profiles/web/cordis.patch.yml`".

### 1.6.3 Configuration steps

1. Click the "**Edit**" button on the red-boxed card
2. **API key**: enter the `user_key` the platform issued you (exactly the same key as `PROXY_USER_KEY` in the CLI-side `.credentials.yaml`)
3. **Expand "Custom settings"** (collapsed by default) and enter the baseURL:
   ```
   http://<proxy-host>:8096/dsh/<spaceId>
   ```
   - ⚠️ **Do not include `/v1`** — the dsh anthropic adapter internally builds `${baseURL}/v1/messages` (source
     `packages/llm/llm-deepseek/src/messages-api.ts:14-17`); including it doubles it to `/v1/v1/messages`
   - For `<spaceId>`, use the memory instance id assigned by the platform (usually `default` or `mem-<...>`)
4. Click "**Save**"

### 1.6.4 Verify

Send "hi"; the proxy should show an `ask_user_question` form. Check the proxy log:

```
[identity] userId=... keyId=... custom=[x-api-key,x-deepseek-harness-session-id,x-deepseek-harness-user-id]
[injection-debug] conversationId=session-<uuid> sessionKey=session-<uuid>
                  agentSource=dsh kind=main dshHeadless=false
                  sessionInitEnabled=true injectedSkipped=false ✓
pipeline.forward.start upstream=https://api.deepseek.com/anthropic/v1/messages
pipeline.forward.done status=200
```

Key fields:
- `custom=[...x-deepseek-harness-session-id,x-deepseek-harness-user-id]` ← only present with the right entry
- `agentSource=dsh` ← determined from the `/dsh/<spaceId>` path segment
- `injectedSkipped=false` ← session-init condition met; the form will appear

Counterexample (when using the third "Custom settings" card):

```
[identity] custom=[x-api-key,x-stainless-arch,x-stainless-lang,...]   ← pi-ai headers, no dsh family
agentSource=dsh injectedSkipped=true                                   ← ★ form does not appear
```

### 1.6.5 Other desktop vs CLI/Web differences

**Fully transparent to the proxy** (research source: `docs/dsh-recon/2026-10-08-dsh-desktop-verification`):

| Dimension | Desktop | CLI/Web | Proxy impact |
|---|---|---|---|
| Built-in tool set | All of Web + `load_workspace_dependencies` + 3 Office skills | Lacks the latter | ❌ None |
| First-frame overlay (5 steps: welcome/credit/purpose/process/done) | ✅ Yes | ❌ No | ❌ Pure UI, no LLM calls |

### 1.6.6 Proxy-side setup

The desktop version doesn't send requests to `copilot.tencent.com` by default — deepseek-official goes to
`https://api.deepseek.com/anthropic`. So in `upstream.agents` of `proxy-service.config.yaml` you
**must configure an explicit upstream for `dsh`**, otherwise it falls back to the outer default `/v2` and returns 404 (tested 2026-10-08):

```yaml
upstream:
  agents:
    dsh:
      # the dsh v0.2+ llm-deepseek-api-key adapter uses Anthropic Messages;
      # proxy anthropic joinUrl auto-appends /v1 → .../anthropic/v1/messages
      url: https://api.deepseek.com/anthropic
      apiKey: sk-<official DeepSeek key>   # with apiKey set → proxy overrides the client Bearer before forwarding
```


## 2. Session ID

| Priority | Header |
|--------|--------|
| 1 | `x-deepseek-harness-session-id` |
| 2 | `x-session-id` |

**When this header is sent** (dsh source `packages/llm/llm-deepseek/src/adapter.ts:129`):
only when the caller (agent loop) passes `options.sessionId`; if it's `undefined`, the header isn't sent. The dsh Web UI
main conversation normally passes it every turn, and auxiliary requests like `title-gen` / `compaction` carry it too (compaction
also carries `x-deepseek-harness-compact: 1`).

⚠️ **Pitfall**: if baseURL points to `/claude-code/<spaceId>` (piggybacking on the CC route) instead of
`/dsh/<spaceId>`, the proxy takes the CC form/extractor branch with `agentSource=claude-code`,
the `ask_user_question` schema doesn't match, and the client reports "unknown tool". Always use the dedicated `/dsh/*`.

## 3. Session Init (session initialization / form)

### 3.1 Mechanism

In preset scenarios (web-app / cordis / standard, etc.), dsh automatically mounts
`@deepseek-ai/dsh-tool-ask-user` (source `packages/interaction/tool-ask-user/src/index.ts`),
which adds an `ask_user_question` tool to the main conversation's tools array. The proxy reuses this native tool name directly
to build a fake tool_use SSE:

- Tool name: **`ask_user_question`** (snake_case, completely different from CC's PascalCase `AskUserQuestion`)
- Tool call id prefix: `call_dsh_session_init_`
- Transport: **Anthropic SSE** (v0.2+, `message_start → thinking → tool_use → message_stop`),
  or OpenAI chat.completion.chunk (v0.1.x compatibility, dispatched by `FormData.protocol`)

### 3.2 ask_user_question schema (dsh hard constraint, incompatible with CC)

```jsonc
{
  "questions": [
    {
      "id": "asset_confirm",       // ← required by dsh, echoed in answer
      "question": "本次对话是否要关联团队资产?",   // "Link team assets for this conversation?" (emitted verbatim by the proxy)
      "header": "关联资产",                       // "Link assets"
      "options": [
        { "label": "是，关联团队资产", "description": "..." },   // "Yes, link team assets"
        { "label": "否，本次不关联",   "description": "..." }    // "No, don't link this time"
      ],
      "multi_select": false          // ← snake_case, not multiSelect
    }
  ]
}
```

tool_result return payload (under the Anthropic protocol, the dsh client puts it in a `type:"tool_result"` block in the
`content[]` of a `role:"user"` message):
```jsonc
{
  "answers": [
    { "id": "asset_confirm", "selected": ["是，关联团队资产"], "custom": "..." }
  ]
}
```

`selected[]` is an **array of selected option label strings** (not indices). `custom` is the free text the user typed in
"Other" (also used as the fallback criterion for skip keywords).

### 3.3 State machine

Reuses the CB state machine (`src/session/codebuddy/init.ts`):

```
uninitialized → pending_asset_confirm → pending_team_select →
pending_agent_task → (optional) pending_task_select → initialized
```

- CB / WB / dsh / opencode / codex share this state machine
- Differences (form shape / transport protocol / tool name) are handled in `src/session/index.ts`, which re-renders `result.response`
  in an `agentSource === "dsh"` branch
- dsh-specific files live in `src/session/dsh/` (form.ts / __tests__/)

### 3.4 Pagination

dsh's `ask_user_question` UI has **no limit on the number of options** (source
`packages/interaction/tool-ask-user/src/index.ts` + the UI QuestionComposer both render via a plain map),
so the dsh form **is not paginated**; all teams/agents/tasks are included. By contrast, CC has a hard limit of ≤4 options
and must paginate.

### 3.5 Headless bypass

dsh has a unique headless bypass:

- Check the `body.tools` array
- If it's non-empty but **does not contain** `ask_user_question` → the proxy treats it as headless, skips session-init entirely and passes through

This lets dsh work normally in direct API / batch mode (custom tools but no interaction tool).

### 3.6 Thinking block required (Anthropic branch)

In thinking mode, DeepSeek's official Anthropic-compatible endpoint **strictly validates** that historical assistant messages
carry a `thinking` block; otherwise it returns 400 `The content[].thinking in the thinking mode must be
passed back to the API`. The fake session-init response the proxy generates (Anthropic branch)
unconditionally emits an empty thinking + placeholder signature block; see the `THINKING_SIGNATURE_PLACEHOLDER` comment in
`src/session/dsh/form.ts`.

The same issue in the OpenAI branch is handled with a `reasoning_content` placeholder (see `REASONING_PLACEHOLDER` in the same file).

### 3.7 Skipping Session Init

Three ways:
1. Headless bypass (no `ask_user_question` in tools) → skipped automatically
2. User types "跳过" ("Skip") / "skip" via the `custom` field
3. Choose "否，本次不关联" ("No, don't link this time") at asset_confirm

## 4. Request classification

dsh uses its own classification logic (`src/agent-adapters/dsh.ts`):

| Type | Detection | Handling |
|------|----------|------|
| **compact** | `x-deepseek-harness-compact: 1` header | Auxiliary request, skip injection |
| **title-gen** | Combined body signature: no tools + thinking.disabled + max_tokens≤128 + system starts with "Create a concise title..." | Auxiliary request, skip injection |
| **main** | Everything else | Full pipeline |

## 5. User text extraction

dsh message content is usually a **plain string** (direct user input) or an **Anthropic content block array**
(when the user message carries a tool_result). The cleaner first scans for tool_result blocks whose `tool_use_id` matches the
`call_dsh_session_init_` prefix, falling back to the text block of the last user message.
See `getLastUserMessageText` in `src/session/codebuddy/cleaner.ts`.

## 6. Injected profile

After session-init completes, the proxy appends the following to the end of the `system` section of Anthropic requests:

```xml
<agent_skills>...</agent_skills>
<user_memory>...</user_memory>
<session_context>...</session_context>
<available_skills>...</available_skills>
<tdai_profile_memory>...</tdai_profile_memory>
```

Injection point: Anthropic `body.system` (dsh v0.2+). The old OpenAI branch injects into `messages[0].content`
(appended inside the system message string, for dsh v0.1.x compatibility).

## 7. Special behavior

- **Protocol**: v0.2+ = **Anthropic Messages** (always sends `anthropic-version: 2023-06-01`);
  v0.1.x = OpenAI Chat. Determined by the upstream dsh adapter; the proxy dispatches by request path
  `/v1/messages` vs `/v1/chat/completions` to `handleAnthropicMessages` or
  `handleChatCompletions`
- **Handler**: v0.2+ uses `src/anthropicHandler.ts` (shared with CC); v0.1.x uses
  `src/handler.ts` (shared with CB)
- **Client fingerprint headers**:
  - `user-agent: deepseek-harness/*`
  - `x-deepseek-harness-user-id` (always sent; anonymous id or logged-in account id)
  - `x-deepseek-harness-session-id` (only sent when `options.sessionId` is present)
  - `x-deepseek-harness-compact: 1` (compaction scenario)
- **Thinking mode**: assistant messages carry a `thinking` block (Anthropic) or a `reasoning_content`
  field (OpenAI); the proxy's fake session-init response must satisfy the upstream strict validation (see 3.6)
- **ask_user_question schema is completely incompatible with CC**: snake_case tool name, required id, array return value
  (see 3.2)

## 10. FAQ

**Q: What causes the client error `unknown tool "AskUserQuestion"`?**
A: dsh v0.2 only recognizes snake_case `ask_user_question`, not CC's PascalCase
`AskUserQuestion`. Check that baseURL points to `/dsh/<spaceId>` (not `/claude-code/<spaceId>`);
only then does the proxy use the dsh form builder and produce the correct tool name.

**Q: Session init keeps popping up the "Link assets?" form in a loop?**
A: Three possibilities:
1. A stale pending_asset_confirm state is stuck in Redis → start a new dsh session
2. The proxy version is too old → you need at least the dsh Anthropic patches after develop_server_team @2026-09-29
3. The dsh baseURL goes through `/claude-code/*`, so agentSource is detected as CC → switch to `/dsh/*`

**Q: dsh shares a state machine with CB; can dsh sessions leak into CB?**
A: No. The state machine code is shared (one CB init.ts), but the session key includes an `agentSource`
prefix (`dsh:<sid>` vs `codebuddy:<sid>`), so they are fully independent in Redis.

**Q: When does the dsh headless bypass trigger?**
A: When `body.tools` is non-empty but doesn't contain `ask_user_question`. Typical scenario: dsh called directly in API mode
(custom tools but no user interaction).

**Q: Why does dsh need a thinking / reasoning_content placeholder?**
A: In thinking mode, DeepSeek's official Anthropic/OpenAI-compatible endpoints strictly
validate assistant messages — they must have a thinking block / reasoning_content field. The session-init
form response generated by the proxy is also an assistant message, so it must carry this field (the value can be empty/a placeholder; the content has no effect on the model,
because the fake session-init never actually goes through the model).

**Q: I'm still on dsh v0.1.x + the old `~/.dsh/settings.yaml`. Will it still work?**
A: Yes. The proxy keeps the OpenAI branch (when FormData.protocol is unset or "openai", it uses the
OpenAI chat.completions SSE builder). But upgrading dsh to v0.2+ and using the Anthropic
protocol is strongly recommended; that's the officially preferred direction.

**Q: The client reports `DeepSeek Messages stream ended before message_stop / STREAM_CLOSED`?**
A: The SSE parser of the dsh v0.2 `llm-deepseek-api-key` adapter (source
`packages/llm/llm-deepseek/src/translate.ts:165`) strictly requires `\n\n` to end an event,
while the old implementation of the proxy's shared mem-command response builder only appended a single `\n` at the end (the CC /
official Anthropic SDK parsers are lenient and don't break; dsh's strict implementation does). Fix: the `maybeFixDshStreamTail` wrapper in `anthropicHandler.ts`
appends one extra `\n` only to stream responses with `agentSource==="dsh"`; the shared builder is untouched byte for byte — zero impact on CC / CB / WB / opencode / codex.
If it still happens after upgrading to develop_server_team @2026-09-30, run `grep -n maybeFixDshStreamTail
src/anthropicHandler.ts` to check whether the wrapper covers the `buildMemResponse`
return point you're hitting (currently all 4 call sites are covered: pre-intercepted unsupported / main mem-command / session
not initialized / _resetFlowResult confirmation response).
