# v3 API Reference · Volume I: MemoryCore

> Service: MemoryCore (memory kernel), port `8420`
> This volume covers every `/v3/*` endpoint exposed by MemoryCore. For MemoryKnowledge (`/v3/wiki`, `/v3/code-graph`, etc.) see Volume II; for MemoryProxy see Volume III.
> Maintenance rule: any API change (new endpoint, changed field, changed error code) must update this document in the same PR.

---

## 1. Common Conventions

### 1.1 Service and Port

| Item | Value |
|---|---|
| Service | MemoryCore (memory kernel gateway) |
| Port | 8420 |
| Method | All `POST` (v3 is RPC-style, no GET) |
| Content-Type | `application/json` |
| Health check | `GET /health` (**not v3**, no auth, returns bare JSON `status/version/uptime/stores/services`; out of scope for this document) |

### 1.2 Response Envelope

Every v3 endpoint returns:

```json
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { } }
```

| Field | Type | Description |
|---|---|---|
| code | number | `0` on success; non-zero on failure. **Note**: the skill module's failure codes are 5-digit numbers (see §1.6) |
| message | string | Always `"ok"` on success; an error description on failure (format in §1.6) |
| request_id | string | Request ID, taken from `x-request-id` or generated by the server |
| data | any | Business payload; usually absent or null on failure |

### 1.3 Pagination

- Data-plane list/query endpoints: `limit` defaults to `20`, max `100`; `offset` defaults to `0` (`paginationSchema`).
- Meta list endpoints: `limit` defaults to `20`, max `100`; `offset` defaults to `0` (`DEFAULT_PAGINATION`); output is always `{ items, total, limit, offset }`.
- Skill `list`: `limit` max `1000`; skill `search`: `top_k` max `50`.
- Knowledge `list`: `pagination.limit` max `1000` (`knowledgeListRequestSchema`, same as skill list).
- memory-prompt / generation-log list: `limit` defaults to `20`, max `100`.

### 1.4 Authentication Tiers

v3 endpoints fall into four auth tiers (all require `Authorization: Bearer <KERNEL_AUTH_TOKEN>` as the Layer 1 gateway check; not enforced when `apiKey` is unset):

| Tier | Routes | Additional auth |
|---|---|---|
| Data plane | `/v3/conversation·atomic·scenario·core/*`, `/v3/session/add`, `/v3/skill/*`, `/v3/knowledge/*`, `/v3/chat-memory/*`, `/v3/memory-prompt/*`, `/v3/memory-generation-log/*` | `x-tdai-service-id` (instance ID) |
| Metadata plane | `/v3/meta/*` | `x-tdai-service-id` + `x-tdai-user-key` (user key; `auth/verify` does not require the user key) |
| Internal ops plane | `/v3/internal/meta/*` | Bearer only; user key is **not parsed** |
| Instance destroy | `/v3/instance/destroy` | Bearer apiKey only (v1-style ops endpoint) |

> Isolation fields: data-plane `team_id / agent_id / user_id / task_id` can be passed in **the body or headers** (`x-tdai-team-id` / `x-tdai-agent-id` / `x-tdai-user-id` / `x-tdai-task-id`); the body takes precedence. The v3 data plane **enforces** team + agent + user triple isolation (missing values fall back to the `default` bucket). Exception: `/v3/session/add` takes isolation fields **from headers only** (`x-tdai-user-id` / `x-tdai-session-id` required, `x-tdai-team-id` optional, no agent); passing `user` / `session` in the body is rejected, and a missing required header returns `400` — see that endpoint's description.

### 1.5 Error Code Semantics (Data Plane)

| code | Meaning |
|---|---|
| 400 | Invalid parameters (missing ID, mutually exclusive fields, empty input) |
| 401 | Authentication failed |
| 403 | Ownership consistency check failed (e.g. `(team_id, agent_id)` is not a valid ownership pair, `task_id` does not belong to `team_id`) |
| 404 | Resource does not exist or does not belong to the current caller context (existence is not disclosed) |
| 409 | Concurrency race timeout |
| 422 | Schema passed but business rule failed |
| 429 | Rate limit / quota exceeded |
| 500 | Internal error |
| 503 | Dependency unavailable (LLM / storage / VDB) |

### 1.6 Error message Formats (Three Kinds, Important)

Failure `message` formats differ by module; the frontend must handle each separately:

| Module | message format | HTTP code | Example |
|---|---|---|---|
| meta / internal-meta | `"{error_code}: {detail}"` (error_code is snake_case) | Standard 4xx/5xx | `"team_not_found: not found: t_1"` |
| skill | Raw `SkillCoreError.message` | **5-digit number** (40001, etc.) | `"SKILL_NOT_FOUND: ..."` |
| data plane / knowledge / chat-memory / memory-prompt / generation-log | Plain text or uppercase enum | Standard 4xx/5xx | `"Knowledge not found"`, `"MEMORY_PROMPT_NOT_FOUND"`, `"Store not available"` |

## 3. Endpoint Details

## 3.1 L0–L3 Data Plane (19)

> Memory layers: L0 raw conversation (conversation), L1 memory atoms (atomic; three kinds: episodic/persona/instruction), L2 scene files (scenario), L3 core persona (core).
> Every endpoint accepts the 4 isolation ID fields (`team_id/agent_id/user_id/task_id`, body or header).
> Delete endpoints such as `conversation/delete` and `atomic/delete` trust Bearer + `x-tdai-service-id` and do no user-level authorization (consistent with the check the panel performs before forwarding).

### POST /v3/conversation/add

Writes L0 raw conversation messages. On success, asynchronously triggers the L1 extraction pipeline (`notifyPipeline`).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| session_id | string | Yes | Business session ID |
| messages | object[] | Yes | 1–100 items, `{ role: "user"\|"assistant", content: 1–8192 chars, timestamp?, recorded_at? }` |
| team_id / agent_id / user_id / task_id | string | No* | Isolation fields (*v3 enforces team+agent+user; missing values fall back to the default bucket) |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| accepted_ids | string[] | IDs of accepted messages |
| accepted_versions | string[] | Same order as accepted_ids; always `v1` for new records |
| total_count | number | Total accepted |

**Example**

```json
// Request
{ "session_id": "sess_1", "messages": [ { "role": "user", "content": "Can you take a look at this bug?" } ] }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "accepted_ids": ["msg_1"], "accepted_versions": ["v1"], "total_count": 1 }
}
```

### POST /v3/conversation/query

Paginated query of L0 messages.

**Request body**: `session_id?`, `limit?` (default 20 / max 100), `offset?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ messages: ConversationItem[], total }`, where ConversationItem = `{ id, version, role, content, timestamp?, recorded_at?, session_id?, team_id?, user_id?, agent_id? }`.

### POST /v3/conversation/search

Keyword search over L0 messages.

**Request body**: `query` (1–2048), `limit?` (default 5 / max 100), `session_id?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ messages: (ConversationItem & { score })[] }`.

### POST /v3/conversation/delete

Batch-deletes L0 by message_ids or session_ids.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| message_ids | string[] | One of the two | ≤5000 items |
| session_ids | string[] | One of the two | ≤100 items |
| session_id | string | No | @deprecated, use session_ids |

**Response** `data`: `{ deleted_count: number }`.

**Errors**: `400` (at least one of the two must be provided).

### POST /v3/conversation/count

L0 count (**v3 only, no v2 entry point**).

**Request body**: `session_id?`, `time_start?`, `time_end?`.

**Response** `data`: `{ total: number }`.

### POST /v3/atomic/update

Updates a single L1 memory atom (version auto-increments).

**Request body**: `id`, `content` (≤8192), `background?` + isolation fields.

**Response** `data`: `{ id, version, updated_at }`, where `version` is a **string** `"v{n}"` (e.g. `"v2"`).

> ⚠️ Inconsistent version type: `update` returns the string `"v{n}"`, but `query`/`search` return a **number** (`r.version ?? 0`). The root cause is in the code (`generated/types.ts` declares `string "v1"`, but `v2-schemas.ts` overrides it to `number`), so the docs cannot satisfy both; the frontend must handle each endpoint separately.

### POST /v3/atomic/query

Paginated query of L1.

**Request body**: `type?` (episodic/persona/instruction), `time_start?`, `time_end?`, `limit?`, `offset?` + isolation fields.

**Response** `data`: `{ items: AtomicDetail[], total }`.

**AtomicDetail** fields:

| Field | Type | Description |
|---|---|---|
| id | string | Atom ID |
| version | number | Current version (**query/search return a number**; note that `update` returns the string `"v{n}"`, an inconsistent type) |
| type | string | `episodic` / `persona` / `instruction` |
| background | string? | Background |
| content | string | Body |
| created_at / updated_at | string | ISO time |
| team_id / agent_id / user_id / task_id | string? | Isolation fields |

**Example**

```json
// Request
{ "type": "episodic", "limit": 20, "offset": 0 }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "rec_1", "version": 1, "type": "episodic", "content": "Release next Monday", "created_at": "2026-08-20T00:00:00Z", "updated_at": "2026-08-20T00:00:00Z" } ],
    "total": 1
  }
}
```

### POST /v3/atomic/search

**Request body**: `query` (1–2048), `limit?` (default 5 / max 100), `type?`, `time_start?`, `time_end?` + isolation fields.

**Response** `data`: `{ items: (AtomicDetail & { score })[] }`.

### POST /v3/atomic/delete

**Request body**: `ids: string[]` (≤5000).

**Response** `data`: `{ deleted_count: number }`.

### POST /v3/atomic/count

L1 count (**v3 only**).

**Request body**: `type?`, `time_start?`, `time_end?`.

**Response** `data`: `{ total: number }`.

### POST /v3/scenario/rm

Deletes an L2 file or directory.

**Request body**: `path` (ending in `/` = delete directory, otherwise delete a single file) + isolation fields.

**Response** `data`: none (`successEnvelope(undefined)`).

### POST /v3/scenario/count

L2 count (**v3 only**).

**Request body**: `path_prefix?`.

**Response** `data`: `{ total: number }`.

### POST /v3/session/add

Writes one session turn (one turn = one user question + everything the agent does for it); each call writes one object. Online sessions are written by MemoryProxy at the end of each turn (`source: online`); cold-start imports call it once per turn (`source: offline`). See `docs/cos-format.md` for object paths and record format, and `docs/session-api.md` for design notes.

Core **does no protocol conversion**; it only validates path segments and top-level record fields, and stores `messages` / `output` content as-is.

**Request headers** (isolation fields are taken from headers only and **not accepted in the body**, unlike other data-plane endpoints)

| Name | Required | Description |
|---|---|---|
| `Authorization` | Yes* | `Bearer <KERNEL_AUTH_TOKEN>`; not enforced when `apiKey` is not configured |
| `x-tdai-service-id` | Yes | Instance ID |
| `x-tdai-user-id` | Yes | User ID, i.e. `user` in the object. Pass `unknown` if unknown |
| `x-tdai-session-id` | Yes | Session ID, i.e. `session` in the object. Sub-agents pass the parent session's ID |
| `x-tdai-team-id` | No | Team ID. Written as `_unassigned` when missing or empty |

ID values (including `subagent` in the body) become path segments: non-empty, at most 256 bytes, no `/`, `\` or control characters, not `.` / `..`. Core does no trimming or escaping; violations return `400`. This endpoint does no user-level auth and trusts Bearer + `x-tdai-service-id`.

**Request body** (limit **32 MiB**, adjustable via env var `MEMORY_SESSION_MAX_BODY_BYTES`; other endpoints remain at 1 MiB)

| Field | Type | Required | Description |
|---|---|---|---|
| source | string | Yes | `online` \| `offline` |
| started_at | string | Yes | Turn start time, fixed format `YYYY-MM-DDTHH:MM:SS.sssZ`; also determines the file name |
| ended_at | string | Yes | Turn end time, same format |
| user_query | string | Yes | The user's question for this turn (plain text); may be an empty string |
| model | string | Yes | Model of the last call in this turn; non-empty |
| messages | array | Yes | Message array sent in the last call of this turn; at least one; content not validated |
| output | object | Yes | Model reply to the last call of this turn; content not validated |
| subagent | string | No | Sub-agent ID, only sent for sub-agent turns; when present must be a non-empty string, not `null` |

Fields outside the table are rejected, including `user` / `session`.

**Persistence**: the body minus `source`, plus `user` / `session` from headers, serialized as UTF-8 JSON and written synchronously under the instance root:

```
sessions/<source>/<team-id>/<user-id>/<session-id>/<started-at>-<id>.json
sessions/<source>/<team-id>/<user-id>/<session-id>/subagents/<subagent-id>/<started-at>-<id>.json
```

`<started-at>` is `started_at` with `-` and `:` removed; `<id>` is an 8-char lowercase hex random value. Instance root: COS `<path-prefix>/<instance-id>/` in service mode; the Gateway data directory (`data.baseDir`, not per-instance) in standalone / open-source mode.

**Not idempotent**: each call generates a new `<id>`, so repeated calls write multiple objects. Callers should only retry on `500` / `503` / network errors.

**Response** `data`

| Field | Type | Description |
|---|---|---|
| object_key | string | Path of the written object (relative to the instance root, excluding `<path-prefix>/<instance-id>/`) |
| bytes | number | Number of bytes written |

**Errors** (no `data` on failure)

| code | Scenario |
|---|---|
| 400 | Missing `x-tdai-service-id` / `x-tdai-user-id` / `x-tdai-session-id` (`missing header: <name>`), invalid path segment, `source` missing or invalid, request body is not valid JSON |
| 401 | Auth failure |
| 413 | Request body exceeds the limit |
| 415 | Unsupported `Content-Encoding` (gzip / deflate supported) |
| 422 | Body is not a JSON object; required field missing, wrong type or format; contains undefined fields or `user` / `session` |
| 503 | Storage unavailable (COS credential / network error, local disk write failure); retryable |
| 500 | Internal error |

**Example**

```json
// Request
// Header: x-tdai-service-id: ins-01
// Header: x-tdai-team-id: team-7
// Header: x-tdai-user-id: 124e14bf
// Header: x-tdai-session-id: 8df5f09b4c614ed19f49697201c39b0b
{
  "source": "online",
  "started_at": "2026-06-11T02:18:20.359Z",
  "ended_at": "2026-06-11T02:18:47.945Z",
  "user_query": "How do I deploy the current binary to machine 10.0.0.1",
  "model": "deepseek-v4-flash-ioa",
  "messages": [ { "role": "user", "content": "How do I deploy the current binary to machine 10.0.0.1" } ],
  "output": { "role": "assistant", "content": "The deployment steps are: …" }
}

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "object_key": "sessions/online/team-7/124e14bf/8df5f09b4c614ed19f49697201c39b0b/20260611T021820.359Z-3f9a1c2e.json",
    "bytes": 1832
  }
}
```

## 3.2 Skill (17)

> Skills use a separate data-plane store (`skill_id` prefix `skl-`); readable within the team, writable by the owner. Identity fields go in the body.
> Failure codes are **5-digit numbers** (see §1.6); the error code mapping is in appendix §4.2.

### POST /v3/skill/create

Creates a skill (on success, automatically registers a meta_asset and binds it to the owner agent).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| name | string | Yes | ≤64 chars, must equal frontmatter.name |
| content | string | Yes | Full SKILL.md text |
| resources | object[] | No | ≤100 items, `{ path ≤512, content, encoding: "utf-8"\|"base64", mime_type?, is_executable? }` |
| metadata | object | No | Custom metadata |
| team_id / agent_id / user_id / task_id | string | See below | Write endpoints require team+agent+user |

> Constraint: `agent_id` must be namespaced by `team_id` (an agent requires a team).

**Response** `data`: `SkillSummary` (see the shared description at the end of §3.2).

**Errors**: `40001` (invalid params / frontmatter mismatch), `42201` (duplicate name), `4291` (quota exceeded), `50304` (repeated skill_id collisions).

**Example**

```json
// Request
{ "team_id": "t_1", "agent_id": "agt_1", "user_id": "u_1", "name": "code-review", "content": "---\nname: code-review\n---\n# Code Review" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "skill_id": "skl_1", "name": "code-review", "version": 1, "status": "active", "owner_user_id": "u_1", "owner_agent_id": "agt_1", "team_id": "t_1" }
}
```

### POST /v3/skill/update

Full update (optimistic locking).

**Request body**: `skill_id`, `expected_version` (≥1), `content` + id fields.

**Response** `data`: `SkillSummary`.

**Errors**: `40901` (stale version; data includes `current_version`), `40401`, `40301`.

### POST /v3/skill/patch

Partial replacement (optimistic locking, string patch).

**Request body**: `skill_id`, `expected_version`, `old_string`, `new_string`, `replace_all?` + id fields.

**Response** `data`: `SkillSummary`.

**Errors**: `40901`, `42202` (patch not unique), `40401`.

### POST /v3/skill/delete

Hard delete (**changed 2026-07; previously a soft delete**): deletes all versions and clears storage, cascading to meta_asset / ACL / agent bindings.

**Request body**: `skill_id`, `expected_version`, `team_id?` + id fields.

**Response** `data`: `{ skill_id, archived: boolean }`; `archived` means "deletion succeeded" (`deleted > 0`) (**not an archived state**; hard deletes reuse this field).

**Errors**: `40401`, `40901`, `40301`, `40302`.

### POST /v3/skill/get

Gets details by skill_id (content / manifest optional).

**Request body**: `skill_id`, `version?`, `include_content?` (default true), `include_manifest?` (default true) + id fields.

**Response** `data`: `SkillSummary + { content?, manifest?, content_hash?, storage_dir? }`.

**Errors**: `40401`.

### POST /v3/skill/get-by-name

Gets details by the unique `(team_id, agent_id, skill_name)` (lets an agent tool call fetch the full text in one go).

**Request body**: `team_id` (required), `agent_id` (required), `skill_name` (≤64), `version?`, `include_content?`, `include_manifest?`.

**Response** `data`: same as `get`.

**Errors**: `40401` (returned uniformly when the name is not found; does not reveal whether the name or the id is missing).

### POST /v3/skill/list

Paginated list (returns only active by default; pass `filters.status` explicitly to include archived).

**Request body**: `filters?` (`{ owner_agent_id?, name_prefix?, status?: ["active"\|"archived"] }`), `pagination?` (`{ limit ≤1000, offset }`) + id fields.

**Response** `data`: `{ items: SkillSummary[], total }`.

### POST /v3/skill/search

Searches skills.

**Request body**: `query` (≤2048), `top_k?` (≤50), `mode?` (bm25/embedding/hybrid), `scope?` (="team" searches team-wide without the owner filter) + id fields.

**Response** `data`: `{ items: (SkillSummary & { score, snippet })[] }`.

### POST /v3/skill/versions

Lists versions.

**Request body**: `skill_id`, `pagination?` + id fields.

**Response** `data`: `{ items: (SkillSummary & { is_expired })[], total }`.

**Errors**: `40401` (skill does not exist).

### POST /v3/skill/files/write

Writes script/resource files.

**Request body**: `skill_id`, `expected_version`, `files` (1–100, same shape as create's resources) + id fields.

**Response** `data`: `SkillSummary`.

### POST /v3/skill/files/remove

Removes files.

**Request body**: `skill_id`, `expected_version`, `paths` (1–100) + id fields.

**Response** `data`: `SkillSummary`.

### POST /v3/skill/files/read

Reads a single file.

**Request body**: `skill_id`, `path`, `version?`, `encoding?` + id fields.

**Response** `data`: `{ content, version, size_bytes, encoding, ... }`.

### POST /v3/skill/export

Exports a skill (zip).

**Request body**: `skill_id`, `version?`, `format?` ("zip" only) + id fields.

**Response** `data`: `{ version, file_count, total_bytes, ... }`.

**Errors**: `41301` (too large).

### POST /v3/skill/listing

Generates the `<available_skills>` injection block (for agent prompts).

**Request body**: `query?` (≤2048), `char_budget?` (0–64000, default 8000) + id fields.

**Response** `data`: `{ mode: "full"\|"search", listing: string, hits: [{ skill_id, version, name }] }`.

### POST /v3/skill/extract

Direct trigger: manually archives one conversation slice (equivalent to one standalone skill extraction).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| user_id / team_id / agent_id | string | Yes | None may contain `\|` |
| messages | object[] | Yes | 1–500 items, `{ role: user\|assistant\|tool_call\|tool_result\|system, content, timestamp?, tool_name?, tool_call_id? }` |
| session_id | string | No | Generated with an `sx-` prefix if omitted |
| space_id | string | No | Falls back to auth.serviceId if omitted |
| task_id / reason / options | — | No | `options.max_iterations` (1–64) |

**Response** `data`: `{ ok: true, task_id, archived_at_ms, archive_key }`.

### POST /v3/skill/conversation/add

Called synchronously at the end of each conversation turn; concatenates, checks thresholds, and archives (the main skill extraction path).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| session_id / user_id / team_id / agent_id | string | Yes | None may contain `\|` |
| messages | object[] | Yes | 1–500 items (roles as in extract; `tool_call`/`tool_result` must include tool_name+tool_call_id) |
| space_id / task_id | string | No | — |

**Response** `data`: `{ status: "ok"\|"archived", archived?: { task_id, archived_at_ms, archive_key, reason } }`, with `archived.reason ∈ tool_calls\|bytes\|compressed\|oversize`.

**Errors**: `40001` (schema/validation), `404` (module not enabled), `50001`.

### 3.7.12 Auth (1)

### POST /v3/meta/auth/verify

Verifies a user_key and returns the caller identity. **No user key required** (the endpoint itself verifies the key; it is on the `V3_NO_USER_KEY_ROUTES` allowlist and handled by the handler rather than the auth middleware).

**Request body**: `{ user_key: string }` (`authVerifySchema`; a missing user_key fails Zod validation → `400`).

**Response** `data`: `{ valid: boolean, user: UserPublic | null }` (**nested, not flat**).

- Valid key: `{ valid: true, user: { user_id, user_type, username, created_at } }`
- Invalid key: `{ valid: false, user: null }` (**still HTTP 200, code=0; does not return 401**)

> ⚠️ The frontend must check `data.valid` and **must not treat an invalid key as a 401 branch**. `401 unauthorized: invalid_user_key` is the behavior of **other meta endpoints** when going through the auth middleware (`x-tdai-user-key` header check), not of `auth/verify` itself.

**Example**

```json
// Request
{ "user_key": "tk_xxx" }

// Response (valid)
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { "valid": true, "user": { "user_id": "usr_1", "user_type": "normal", "username": "zhangsan", "created_at": "2026-08-20T00:00:00Z" } } }

// Response (invalid key; note code is still 0)
{ "code": 0, "message": "ok", "request_id": "abc-123", "data": { "valid": false, "user": null } }
```
