# MemoryPanel API Reference

> Service: MemoryPanel (control panel), port `8125`

---

## 1. Common conventions

### 1.1 Base URL and port

| Item | Value |
|---|---|
| Base URL | `/api/v1` (except `/health`) |
| Port | 8125 |
| Method | **Everything is `POST`** (RPC style) except `GET /health` and `GET /api/v1/meta/instances` |
| Content-Type | `application/json` |

### 1.2 Authentication

Most business endpoints rely on the following headers (validated by the `validatePanelMetaHeaders` middleware):

| Header | Required | Description |
|---|---|---|
| `x-tdai-service-id` | Yes | Instance ID, used to locate the target kernel gateway (`instanceRegistry.resolve`) |
| `x-tdai-user-key` | Yes* | Current user key, used by the kernel-side `auth/verify` to resolve the caller identity |
| `x-request-id` | No | Passed through to the response envelope's `request_id` for log correlation |

> `*` Exceptions: `POST /meta/auth/verify` (no user-key required, since it is the endpoint that verifies the key); `POST /knowledge/status-callback` (S2S callback, no browser headers); `GET /health` and `GET /meta/instances` (no auth).

### 1.3 Response envelope

All business endpoints return:

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { }
}
```

| Field | Type | Description |
|---|---|---|
| code | number | `0` on success; non-zero on failure |
| message | string | Always `"ok"` on success; on failure an UPPER_SNAKE_CASE error enum (a stable contract that the frontend branches on) |
| request_id | string | Request ID, taken from `x-request-id` or generated by the server |
| data | any | Business data; `null` on failure |

> Exception: `GET /health` and `GET /meta/instances` **do not return an envelope**; they return bare JSON (see §3.1).

### 1.4 HTTP status mapping

Mapping rule for `HTTP status = envelope.code`:

| envelope.code | HTTP status |
|---|---|
| `0` | `200` |
| `400 ~ 599` | Same as `code` |
| Anything else | `502` |

### 1.5 Pagination

- Kernel list endpoints default to `DEFAULT_PAGINATION = { limit: 20 }`: **if the frontend calls a `meta/*` list action directly without `limit`, only the first 20 items are returned**.
- Panel-level aggregation/business endpoints (e.g. `chat-memory/*`, `knowledge/*/team-assets`) already page through everything internally, so the frontend doesn't need to paginate.
- The `limit` cap for `task/list-with-agents` is 200; when omitted, the kernel returns the default 20 items but the response `limit` field echoes 50 (a known inconsistency, see §3.5).

### 1.6 Idempotency

- Knowledge create endpoints (`wiki/create`, `code-graph/create`) are idempotent by same name/same resource: a duplicate create returns the existing resource instead of an error.
- Create `meta/*` actions (`user/create`, `team/create`, `agent/create`, `task/create`) check for duplicates in the Panel layer first, and a duplicate name returns `409` with a Chinese message (see §4.2).

### 1.7 Request ID chain

`x-request-id` (optional) → passed through into the envelope's `request_id` → also carried when forwarding to the kernel, for cross-service log correlation.

## 3.2 Transparent metadata proxy

### POST /meta/*

Forwards `{ action, ...payload }` to the kernel's `/v3/meta/{action}` and passes the envelope through unchanged. This is the Panel's single entry point to the kernel metadata plane (user/team/agent/task/asset/acl, etc.).

**Auth**: `x-tdai-service-id` + `x-tdai-user-key` (only `auth/verify` is exempt from the user-key).

**Forwarding semantics**:
- The whole request body is passed through to the matching kernel action; the response envelope is returned unchanged.
- The last path segment is the action name (e.g. `POST /meta/agent/list` → kernel `agent/list`).
- Actions outside the allowlist return `404 UNKNOWN_META_ACTION`; `agent-fixed-asset/*` returns `501 NOT_IN_SCOPE` (these operations are called directly inside Panel business routes, see §3.4/§3.10).

**Exposed actions (53)**:

| Entity | action |
|---|---|
| user | create, create-with-key, get, delete, list |
| user-key | create, list, get, revoke, update |
| team | create, get, update, delete, list |
| team-member | add, remove, list, get |
| agent | create, get, update, delete, list, archive, set-default-template, get-default-template |
| task | create, get, update, delete, list, archive |
| task-agent | link, unlink, list |
| participation-log | append, list |
| asset | create, get, update, delete, list, list-accessible, touch-usage |
| acl | grant, revoke, list, check |
| auth | verify |
| instance-quota | get |
| config/user | get, set |

**Not exposed (`501 NOT_IN_SCOPE`)**: `agent-fixed-asset/set`, `agent-fixed-asset/list`, `agent-fixed-asset/list-with-detail`, `agent-fixed-asset/summary-by-agents`.

**Panel-layer special handling (not pure passthrough)**:

| action | Behavior |
|---|---|
| `user/create`, `user/create-with-key`, `team/create`, `agent/create`, `task/create` | First checks for duplicates by name/username/title; a duplicate returns `409` with a Chinese message (see §4.2) |
| `agent/set-default-template` | **Not forwarded to the kernel**; the Panel writes the template file locally. Requires `system_admin`, otherwise `403 permission_denied`; missing `team_id`/`template` returns `400 INVALID_PARAM` |
| `agent/get-default-template` | **Not forwarded to the kernel**; the Panel reads the template file locally |
| `team-member/add` | On success, asynchronously copies template assets to the default Agent (best-effort) |
| `user/list` | Hides the internal `knowledge-service` billing user |

**Example** (`agent/create`):

```json
// Request
POST /api/v1/meta/agent/create
{ "team_id": "t_1", "owner_user_id": "u_1", "name": "Release assistant" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "agent_id": "agt_xxx", "name": "Release assistant" }
}
```

## 3.3 Transparent Skill data-plane proxy

### POST /skill/*

Forwards `{ action, ...payload }` to the kernel's `/v3/skill/{action}` and passes the envelope through unchanged.

**Auth**: `x-tdai-service-id` + `x-tdai-user-key` (mandatory; skills need the owner identity).

**Differences from `/meta/*`**:
- The Skill data plane has its own storage (`skill_id` prefix `skl-`): readable within the team, writable by the owner agent.
- Identity fields (`user_id` / `team_id` / `agent_id` / `task_id`) go in the **body**, not in headers.
- Pagination uses nested `pagination.{limit, offset}`; the body is passed through unchanged.

**Exposed actions (15)**:

| action | Description |
|---|---|
| create | Create a skill |
| update | Full update |
| patch | Partial update |
| delete | Delete |
| get | Get one |
| list | Paginated list |
| search | Search |
| versions | Version list |
| files/write | Write a file |
| files/remove | Remove a file |
| files/read | Read a file |
| listing | Directory listing |
| extract | Extract |
| export | Export |
| conversation/add | Append conversation (main skill extraction path; added to the allowlist in 2026-08) |

**Errors**: an unknown action returns `404 UNKNOWN_SKILL_ACTION`.

**Example** (`list`):

```json
// Request
POST /api/v1/skill/list
{
  "user_id": "u_1",
  "team_id": "t_1",
  "filters": { "status": ["active"] },
  "pagination": { "limit": 50, "offset": 0 }
}

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "skill_id": "skl_1", "name": "code-review", "owner_agent_id": "agt_1" } ],
    "total": 1
  }
}
```

## 3.4 Chat-Memory

> Common output shape of a memory block (MemoryBlock):

| Field | Type | Description |
|---|---|---|
| id | string | Asset ID (`chat_memory-{team}-{agent}` or user-created `mem-xxx`) |
| title | string | Block title |
| summary | string | Summary (currently placeholder text: the server returns the literal `"0 条 L1 · 0 条 L2 · 0 条 L3"`, i.e. "0 L1 · 0 L2 · 0 L3 items") |
| uploaded_by_user_id | string | Owner user ID |
| updated_at_ms | number | Update time (ms epoch) |
| layer_counts | object | `{ L0_messages, L1, L2, L3 }` (currently a placeholder, all 0) |
| scope | string | `team` / `private` |
| agent_id | string | Associated agent (returned by some endpoints) |

### POST /chat-memory/team-assets

List of memory assets shared with the team (`visibility=team`, regardless of owner). **Note: the MemoryBlocks returned by this endpoint have no `scope` field** (everything in the Team Assets tab is shared by definition).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | Yes | Team ID |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| items | MemoryBlock[] | Team-shared memory blocks (no `scope`) |
| total | number | Total count |

**Example**

```json
// Request
{ "team_id": "t_1" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "items": [ { "id": "chat_memory-t_1-agt_1", "title": "Release assistant", "summary": "0 条 L1 · 0 条 L2 · 0 条 L3" } ],
    "total": 1
  }
}
```

> `summary` above is the literal placeholder the server returns ("0 L1 · 0 L2 · 0 L3 items").

### POST /chat-memory/agent-fixed

List of fixed asset bindings of type `chat_memory` under a given Agent. **Visible only to the Agent owner**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| agent_id | string | Yes | Agent ID |

**Response** `data`: `{ items: MemoryBlock[], total }`. Each item includes `scope` (`team`/`private`) so the frontend can gray out entries that the owner has set to private.

**Errors**: `MISSING_AGENT_ID`, `INVALID_USER_KEY`, `AGENT_NOT_FOUND`, `NOT_YOUR_AGENT`.

### POST /chat-memory/my-agents

"My Assets" tab: returns all Agents I own, one memory block per Agent (`block.id = chat_memory-{team}-{agent}`).

**Request body**: `{ team_id: string }`

**Response** `data`: `{ items: MemoryBlock[], total }`. Each item includes `agent_id` and `scope` (from the visibility of that agent's own memory).

**Errors**: `MISSING_TEAM_ID`, `INVALID_USER_KEY`.

### POST /chat-memory/mine

List of memory assets owned by me.

**Request body**: `{ team_id: string }`

**Response** `data`: `{ items: MemoryBlock[], total }`.

**Errors**: `MISSING_TEAM_ID`, `INVALID_USER_KEY`.

### POST /chat-memory/create

Creates a standalone memory asset (UserAsset, `mem-xxx`).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | Yes | Team ID |

| scope | string | No | `team` (default) / `private` |
| description | string | No | Description |

**Response** `data`: `MemoryBlock` (`id` is the new `mem-xxx`).

**Errors**: `MISSING_TEAM_ID`, `INVALID_TITLE`, `INVALID_USER_KEY`.

**Example**

```json
// Request
{ "team_id": "t_1", "title": "Product requirement notes", "scope": "team" }

// Response
{
  "code": 0,
```

### POST /chat-memory/import

Imports conversation history into the L0 of an Agent's memory pool (via the data-plane `/v3/conversation/add`; no new asset is created).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| team_id | string | Yes | Team ID |
| agent_id | string | Yes | Target Agent |
| messages | object[] | Yes | `[{ role, content, ts? }]`, ≤ 100 items |
| session_id | string | No | Session ID; defaults to an auto-generated `imported-{ts}` |

**Response** `data`

| Field | Type | Description |
|---|---|---|
| imported | boolean | Always `true` |
| block_id | string | `chat_memory-{team}-{agent}` |
| session_id | string | Actual session |
| accepted_count | number | Number of items written successfully |

**Errors**: `MISSING_TEAM_ID`, `MISSING_AGENT_ID`, `MISSING_MESSAGES`, `TOO_MANY_MESSAGES`, `NO_VALID_MESSAGES`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`.

**Example**

```json
// Request
{
  "team_id": "t_1",
  "agent_id": "agt_1",
  "messages": [ { "role": "user", "content": "Can you take a look at this bug?" } ]
}

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "imported": true, "block_id": "chat_memory-t_1-agt_1", "accepted_count": 1 }
}
```

### POST /chat-memory/patch-scope

Changes memory visibility (team ↔ private).

**Request body**: `{ block_id: string, scope: "team" | "private" }`

**Response** `data`: `{ updated: true, id, scope }`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_SCOPE`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`.

### POST /chat-memory/set-agent-fixed

Batch-sets an Agent's fixed memory (atomic validation + a single full set).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| agent_id | string | Yes | Target Agent |
| team_id | string | Yes | Team ID |
| block_ids | string[] | Yes | Memory block IDs to bind (including its own `chat_memory-{team}-{agent}`) |

**Response** `data`: `{ updated: true, agent_id, block_ids }`.

**Errors**: `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `IMPORT_LIMIT_EXCEEDED`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `TEAM_MISMATCH`, `ASSET_NOT_SHARED`.

### POST /chat-memory/allocate

Allocates (imports) a shared memory block to a given Agent. Enforces the "at most 2 imports" check.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| agent_id | string | Yes | Target Agent |
| team_id | string | Yes | Team ID |

**Response** `data`: `{ allocated: true, agent_id, block_id }`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `TEAM_MISMATCH`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `ASSET_NOT_SHARED`, `IMPORT_LIMIT_EXCEEDED`. A duplicate allocation returns `409` with the Chinese message `"这条记忆已经分配给该 Agent，无需重复分配。"` ("This memory is already allocated to this Agent; no need to allocate it again."); allocating an agent's own `chat_memory-{team}-{agent}` back to itself returns `400` with the Chinese message `"不能把该 Agent 自己的记忆再分配给自己。"` ("You can't allocate this Agent's own memory to itself.").

**Example**

```json
// Request
{ "block_id": "chat_memory-t_1-agt_2", "agent_id": "agt_1", "team_id": "t_1" }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": { "allocated": true, "agent_id": "agt_1", "block_id": "chat_memory-t_1-agt_2" }
}
```

### POST /chat-memory/unbind

Unbinds an imported memory from an Agent.

**Request body**: `{ block_id: string, agent_id: string, team_id: string }`

**Response** `data`: `{ unbound: true, agent_id, block_id }`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_AGENT_ID`, `MISSING_TEAM_ID`, `CANNOT_UNBIND_SELF_CHAT_MEMORY`, `AGENT_NOT_FOUND`, `AGENT_NOT_IN_TEAM`, `NOT_YOUR_AGENT`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `BINDING_NOT_FOUND`.

### POST /chat-memory/layer

Lazy-loads memory content by layer. Resolves team/agent from `block_id`, then calls the kernel data plane.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | Yes | `L0` / `L1` / `L2` / `L3` |
| limit | number | No | Valid range `(0, 200]`; when omitted, ≤0 or >200 it falls back to 50 (not clamped, unlike the clamp semantics of task/search) |
| offset | number | No | Default 0 |
| before_ts | string | No | L0 cursor pagination (ISO8601; to page, pass the timestamp of the last item on the previous page) |
| time_start | string | No | Time filter start (L0/L1 only) |
| time_end | string | No | Time filter end (L0/L1 only) |
| path | string | No | File path when reading a single L2 item |

**Data source per layer**: L0 → `/v3/conversation/query`; L1 → `/v3/atomic/query`; L2 → `/v3/scenario/ls` (list) / `/v3/scenario/read` (with `path`); L3 → `/v3/core/read`.

**Response** `data`: `{ layer, items, total, limit, offset }`. Shape of each `items` entry:

| Field | Type | Description |
|---|---|---|
| id | string | Item ID (always `"core"` for L3) |
| title | string | Title (role@session for L0, type for L1, path for L2, always `"core memory"` for L3) |
| role | string? | L0 only: message role (`user`/`assistant`/`tool`, etc.) |
| body | string | Content |
| tags | string[] | Tags |
| refs | string[] | References (currently always empty) |
| created_at | string | Time (ISO) |

**Read permission**: any one of owner / `visibility=team` / already imported by an agent owned by the caller; otherwise `403 ASSET_NOT_ACCESSIBLE`.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `ASSET_NOT_ACCESSIBLE`, `RANGE_TOO_LARGE` (time filter range too large for the VDB to handle), `LAYER_FETCH_ERROR`.

**Example** (L1)

```json
// Request
{ "block_id": "chat_memory-t_1-agt_1", "layer": "L1", "limit": 20, "offset": 0 }

// Response
{
  "code": 0,
  "message": "ok",
  "request_id": "abc-123",
  "data": {
    "layer": "L1",
    "items": [ { "id": "rec_1", "title": "atomic", "body": "Release next Monday", "tags": [], "refs": [] } ],
    "total": 1,
    "limit": 20,
    "offset": 0
  }
}
```

### POST /chat-memory/clear

Clears all content of one or more memories in one click while keeping the assets themselves (ownership/bindings/ACL unchanged). **Asset owner only**.

**Request body**: `{ memory_ids: string[] }` (≤ 100 after de-duplication).

**Response**: passes through the kernel `/v3/chat-memory/clear` result.

**Errors**: `MISSING_MEMORY_IDS`, `TOO_MANY_MEMORY_IDS`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `CLEAR_FAILED`.

### POST /chat-memory/layer-delete

Batch delete from the L0/L1 lists. **Asset owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | Yes | `L0` / `L1` |
| message_ids | string[] | For L0 | Message IDs, ≤ 5000 |
| session_ids | string[] | For L0 | Session IDs, ≤ 100 |
| ids | string[] | For L1 | Record IDs, ≤ 5000 |

**Response**: passes through the kernel `/v3/conversation/delete` or `/v3/atomic/delete` result (including `deleted_count`).

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `TOO_MANY_IDS`, `MISSING_IDS`, `LAYER_DELETE_FAILED`.

### POST /chat-memory/layer-update

Edits the memory content of a single layer. **Asset owner only**.

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | Yes | `L1` / `L2` / `L3` |
| id | string | Required for L1/L2 | L1 record primary key / L2 file path |
| content | string | Yes | New content |
| summary | string | No | L2 summary |

**Data source per layer**: L1 → `/v3/atomic/update`; L2 → `/v3/scenario/write` (META header stripped automatically); L3 → `/v3/core/write`.

**Response**: passes through the result of the matching kernel write endpoint.

**Errors**: `MISSING_BLOCK_ID`, `INVALID_LAYER`, `MISSING_CONTENT`, `MISSING_ITEM_ID`, `NOT_AGENT_MEMORY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `NOT_ASSET_OWNER`, `LAYER_UPDATE_FAILED`.

### POST /chat-memory/search

Keyword search by layer (agent-scoped recall across sessions).

**Request body**

| Field | Type | Required | Description |
|---|---|---|---|
| block_id | string | Yes | Memory block ID |
| layer | string | No | `L0` / `L1`, default `L1` |
| query | string | Yes | Search term |
| limit | number | No | Default 30, max 100 |
| type | string | No | L1 type filter |

**Response** `data`: `{ items, total }`. Each `items` entry includes `score` (relevance); an L1 `id` can be used directly with `layer-update`.

**Errors**: `MISSING_BLOCK_ID`, `MISSING_QUERY`, `BLOCK_NOT_FOUND`, `NOT_CHAT_MEMORY`, `ASSET_NOT_ACCESSIBLE`, `SEARCH_FAILED`.

**Example**

```json
// Request
{ "block_id": "chat_memory-t_1-agt_1", "layer": "L1", "query": "release" }
```

### 4.2 Error message enum summary

> `message` is a stable contract that the frontend branches on; new error codes must be added to this table.
>
> Note three `message` format exceptions (all assembled by the Panel, not pure enums):
> 1. **Data-plane failures** (`LAYER_FETCH_ERROR` / `CLEAR_FAILED` / `LAYER_DELETE_FAILED` / `LAYER_UPDATE_FAILED` / `SEARCH_FAILED`): the actual value is `"<CODE>: <err.message>"` (with a `: details` suffix), so the frontend should use `startsWith(CODE)` rather than an exact match.
> 2. **400 from `POST /knowledge/status-callback`**: `message` is a lowercase English sentence (`"wiki_id and progress fields are required"` / `"knowledge_id, type, status are required"`), not an enum. This endpoint is an S2S callback that the frontend doesn't consume directly, so it can be ignored.
> 3. **Chinese sentences** (`respondControlError` puts Chinese text directly into `message`; not an enum, and `startsWith(CODE)` won't match either): the `meta/*` create duplicate-check 409 (`"已存在同名{entity}「{name}」，请更换名称后重试。"`, "A {entity} named '{name}' already exists; please choose a different name and retry", where `{entity}` is e.g. `用户` (user) or `团队` (team)), the `chat-memory/allocate` duplicate-allocation 409 (`"这条记忆已经分配给该 Agent，无需重复分配。"`, "This memory is already allocated to this Agent"), and the self-allocation 400 (`"不能把该 Agent 自己的记忆再分配给自己。"`, "You can't allocate this Agent's own memory to itself"). The frontend must fall back on the message text or the HTTP status; it can't branch on a CODE enum.
